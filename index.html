QR-NATIVE GAME DEVELOPMENT

Build games that fit in a QR code.

Write QG, compile to binary, encode as Base39, and decode the actual payload into a playable browser game. The preview runs the decoded result.

Language guide

QG is a compact programming language for browser games. Its compiler converts source code into binary instructions, encodes them using Base39, and stores the result in a URL. Opening that URL reconstructs a playable HTML game.

1. Getting started

Every game begins by declaring its canvas. Coordinates start at the upper-left corner. X increases rightward and Y increases downward. The generated webpage scales the canvas to fit the available screen while preserving its proportions. 

canvas(400,440);
rect(0,0,400,440,"#25221f");
text("Hello QG",20,30,"#ead4b6");

The first two canvas arguments are the logical width and height. Drawing uses these coordinates regardless of the phone's physical screen resolution.

2. Variables and data types

Declare mutable variables using let. QG supports numbers, strings, booleans, null, arrays, and function values. Arrays use zero-based indexing and can be modified. 

let score=0;
let player=[100,200,5];
let alive=true;

score=score+10;
player[0]=player[0]+5;
player.push(20);
let last=player.pop();

Variable names are replaced with compact numeric IDs during compilation. Function-local variables and parameters use six-bit identifiers, allowing up to 64 local slots per function. Original variable names are not preserved when decoding.

3. Math and operators

QG supports arithmetic, comparisons, and logical operations. Expressions are encoded as compact binary instructions rather than storing their original JavaScript-like text. 

let x=10+5*2;
let y=floor(x/3);
let distance=abs(x-y);

if(x>10&&y<20){
  x=x+1;
}

Arithmetic: +, -, *, /, %. Comparisons: ==, !=, <, >, <=, >=. Logic: &&, ||, !. Frequently used small integers have shorter encodings.

4. Functions, loops and recursion

Functions are declared with fn and can return values. Use if/else for conditions, for for counted loops, and while for condition-based loops. Recursive functions are supported, making QG suitable for search algorithms and game AI. 

fn factorial(n){
  if(n<=1){return 1;}
  return n*factorial(n-1);
}

let result=factorial(5);

for(let i=0;i<8;i=i+1){
  result=result+i;
}

while(result>100){
  result=result-10;
}

Nested functions that capture local variables from surrounding functions are not supported by the current codec. Use explicit function parameters or global state instead.

5. Sprite sheets

Sprites are stored as rectangular grids of digits. Every row must have the same width. Each digit is a palette index from 0 to 4: zero is transparent and 1–4 are visible colors. Sprites can be any supported rectangular size, including 8×8 and 16×16. 

palette ivory=[
  null,
  "#ead4b6",
  "#55483e"
];

sprite pawn(ivory){
00011000
00111100
00111100
00011000
00111100
01111110
01111110
12222221
}

blit(pawn,20,20,5);

The blit arguments are sprite, X position, Y position, and scale. An 8×8 sprite drawn at scale 5 occupies 40×40 logical pixels.

The compiler compares base-5 pixel packing with run-length encoding and uses the smaller representation. This is especially effective for sprites with large transparent regions or repeated colors.

6. Palette swapping and sprite reuse

A sprite can be drawn using a different palette without storing its pixel pattern again. This is useful for different teams, character colors, chess pieces, enemy variations, and animations. 

palette ivory=[
  null,
  "#ead4b6",
  "#55483e"
];

palette charcoal=[
  null,
  "#343039",
  "#c2a88d"
];

sprite pawn(ivory){
00011000
00111100
00111100
00011000
00111100
01111110
01111110
12222221
}

blit(pawn,20,20,5);
blit(pawn,80,20,5,charcoal);

The optional fifth argument to blit overrides the sprite's original palette. Both calls use the same stored pixel data. Palette colors are compressed into RGB555 values, using five bits for each red, green and blue channel.

7. Drawing and colors

Use rect to draw filled rectangles, text to display labels, clear to clear the canvas, and blit for sprites. Rectangles and text can use hexadecimal color strings or built-in numeric color IDs. 

rect(0,0,400,400,"#25221f");
rect(10,10,50,50,"#665448");
text("Score: "+score,10,420,"#ead4b6");

Hexadecimal colors provide precise control. Numeric drawing colors use the runtime's fixed palette; sprite palette declarations do not automatically change those numeric drawing colors. Clearing the canvas makes it transparent, so draw a background afterward when necessary.

8. Touch input and animation

touch registers a callback for pointer presses. Its X and Y arguments use logical canvas coordinates. frame registers a callback executed every animation frame. Its dt argument represents elapsed seconds. 

let x=100;
let dirty=1;

touch(fn(tx,ty){
  x=tx;
  dirty=1;
});

frame(fn(dt){
  if(dirty){
    rect(0,0,400,400,"#25221f");
    rect(x,100,30,30,"#b69a58");
    dirty=0;
  }
});

Turn-based games should generally redraw only when something changes. A dirty flag avoids unnecessary drawing and can reduce flickering. Expensive AI searches should not run continuously inside frame callbacks.

9. Built-in functions

Graphics: canvas, clear, rect, text, blit. Events: touch, frame. Math: floor, abs, min, max, sin, cos, sqrt, rand. Arrays: len, push, pop, .length, .push(), .pop(). 

let x=floor(rand()*100);
let y=max(0,min(x,50));
let a=[1,2,3];
a.push(y);
let count=len(a);

QG is not full JavaScript. DOM access, imports, arbitrary browser APIs, and unsupported JavaScript syntax cannot be used directly in QG programs.

10. Binary compression

QG compiles source code into an abstract syntax tree, assigns numeric IDs to symbols, encodes operations using prefix-free variable-length instructions, and packs the resulting bits into Base39.

Common small numbers use short encodings. Other integers use variable-length representations. Colors use RGB555. Sprite pixels use base-5 packing or run-length encoding. Arrays and expressions are encoded structurally.

Compression is not guaranteed to make every game fit inside one QR code. Large sprites, long strings, complex AI and repeated logic still consume space. Always inspect the actual compiled Base39 length.

11. Compiling and testing games

Paste QG source into the editor and select Compile and preview. The website displays the compiled bit count, Base39 payload length, decoded QG source and executable game preview.

To test locally, open a terminal in the project folder: 

cd C:\Projects\QR-code-to-game
npx wrangler pages dev .

Open http://localhost:8788 in your browser. Generated games use /0/ followed by their Base39 payload. Keep the _redirects file in the site root so direct links can load the decoder.

QG v2 — Binary specification

This is the actual encoder used by this page, not a proposed future format. The codec is versioned: /0/ is the optimized binary format, /1/ is the earlier AST prototype, and /0/ is reserved for your original Huffman format.

1. End-to-end encoding

QG source → parsed AST → symbol IDs → prefix-coded operations and typed values → packed bitstream → Base39. The decompiler reverses the bitstream into QG with generated names (v0, l0, f0, p0, s0), then produces executable HTML. The preview always uses the decoded data.

2. Symbol IDs and scope

Each reference stores a 3-bit category plus 6-bit ID: global variable, function-local variable, user function, built-in function, palette, or sprite. The 6-bit IDs permit 64 symbols per category or local frame. Identifiers are discarded; they are not stored as strings. Function arguments and local declarations use 6-bit local slots. Built-ins use fixed IDs. Nested function closures capturing non-global local variables are not supported in v2.

3. Instruction opcodes

AST instructions use fixed, prefix-free variable-length opcodes instead of 5-bit tags. The most common instructions get 3–4 bits. All operands follow their opcode, and counted lists use unsigned varints.

Binary operators are currently stored as 4-bit IDs; a future version can use frequency-derived prefix codes for those too.

    
4. Numbers, strings, arrays, and properties
Numbers 0–4 use a 1-bit type flag plus 3 value bits. Signed integers -16 to 15 use 2 type bits plus 5 value bits. Other safe integers use zigzag varints, while nonintegers use IEEE-754 float64. String literals use UTF-8 bytes with varint length; actual text content cannot be eliminated. Arrays store a varint element count followed by encoded expressions. Common properties push, pop, and length use short IDs; uncommon property names remain UTF-8 strings.

    
5. RGB555 palettes and sprite compression
Palette entries use a 1-bit presence flag; opaque colors use exactly 15 additional bits (RGB555). Transparency is explicit. RGB555 rounds 8-bit color channels to 5 bits, so decompiled hex colors can differ slightly. Sprite dimensions use varints, and pixels are stored as either base-5 packed digits or run-length encoding, whichever is smaller for that sprite. Each pixel is a palette index 0–4, where 0 is transparent.

    
6. Base39 and URL versions
Alphabet: 0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ*+-. A leading sentinel bit 1 is prepended to the packed binary before conversion to a Base39 integer, preserving all leading zero bits. The URL form is /0/BASE39. /1/ keeps the earlier AST decoder. /0/ is reserved for the original tree/Huffman decoder and must be integrated separately to play old links.

    
7. Compatibility, constraints, and remaining optimization
The first 4 bits are the binary format version (2), followed by 4 reserved zero flag bits. The codec is fixed once published. No full identifier strings are stored. This format is more compact structurally than the AST prototype, but it is not proven smaller than the existing Huffman QG pipeline without a corpus benchmark. Operator IDs, function-call argument counts, and node-count varints remain optimization opportunities. QG v2 is a new format, not a decoder for existing /0/ games.
